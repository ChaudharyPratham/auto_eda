What is Auto EDA?

Your elevator pitch — practice saying this out loud in 30 seconds.

🎯
30-Second Pitch (memorise this)
"Auto EDA is a full-stack web application I built that automates exploratory data analysis. You upload any dataset — CSV, Excel, Parquet, Avro, or even pull directly from AWS S3 or Azure — and the platform instantly gives you statistical summaries, interactive visualizations, and a smart cleaning panel that detects issues and lets you selectively fix them. 2. Statistical Analysis

The analysis service runs on the loaded DataFrame and computes:

shape          → row count, column count
dtypes         → data type per column (int, float, object, datetime)
missing        → count and % of nulls per column
duplicates     → total duplicate rows
describe()     → mean, std, min, 25%, 50%, 75%, max for numeric columns
corr()         → Pearson correlation matrix
IQR outliers   → values outside Q1 - 1.5×IQR or Q3 + 1.5×IQR per column

3. Selective Cleaning (Key Feature)

Unlike "clean everything" tools, Auto EDA scans first, then asks. The cleaning flow has two steps:

Operation IDs returned by the scan:

Each operation has a severity: 🔴 error (>10% affected), 🟡 warning (moderate), 🔵 info (minor).

4. Visualizations

Charts are generated server-side from the data and returned as JSON configs. The frontend renders them with Plotly.js. Each chart has a PNG download button that uses Plotly.downloadImage() at 2× retina resolution.

6. Cloud Import (Single File + Full Folder)

Users paste a URI and select a provider. The backend downloads the file(s) using the corresponding SDK (credentials from .env), saves to uploads/, and routes exactly like a local upload. Folder imports list all blobs/objects under a prefix and download all of them.

7. Data API with API Key Auth

After cleaning, users can generate a per-dataset API key. The key is shown once, then only its SHA-256 hash is stored. External apps can then call:

GET /api/data/{file_id}?page=1&page_size=100
Header: X-API-Key: sk_abc123...

8. Image Dataset Analysis

Upload a folder of images (PNG/JPG/BMP/WebP). The backend uses Pillow to detect: image count per class (folder), resolution stats, corrupted files, and duplicate images (via pixel hash). Outputs a clean ZIP download of valid images.

9. ⚡ Streaming Analytics

A real-time log ingestion and monitoring pipeline built on Apache Kafka + PySpark Structured Streaming + PostgreSQL.

Architecture

External App → POST /api/stream/ingest (X-API-Key) → FastAPI → stream_events table + Kafka "logs" topic Mock producer.py → Kafka "logs" topic (2 msg/s) Kafka → spark_consumer.py (PySpark) → 1-min tumbling window → stream_metrics + stream_alerts Frontend → polls /api/stream/latest every 5 s → live KPI cards + anomaly alert banners

How it works under the hood

  • Kafka producer — Python script that generates mock log events (INFO/WARNING/ERROR) at 2/sec with randomised services and response times. Uses weighted random selection: INFO 70%, WARNING 20%, ERROR 10%.
  • Kafka consumer (PySpark) — reads from the logs topic using Structured Streaming, applies a window(col("ts"), "1 minute") tumbling aggregation, computes count, sum(is_error), avg(response_time) per window, then writes to PostgreSQL using foreachBatch.
  • Anomaly detection — inline in the Spark job: if error_rate > 30% or avg_response_time > 1000ms, an alert row is inserted into stream_alerts.
  • REST ingest API — POST /api/stream/ingest accepts JSON events from external applications. Requires an X-API-Key header. The key is validated by comparing SHA-256 hashes (never stores plain text). Validated events are saved to stream_events and forwarded to Kafka.
  • API key lifecycle — keys are created via POST /api/stream/api-key. Only the SHA-256 hash is persisted; the plain key is returned once and never retrievable again. Keys can be revoked (soft-deleted) at any time.
  • Service filtering — the dashboard filter sends ?service=payment. The backend queries stream_events (raw events) for per-service metrics, making filtered views accurate even for data that hasn't yet reached a full aggregation window.

API Key Security

When a user clicks "Generate API Key":

# 1. Generate a cryptographically random key
raw_key = secrets.token_urlsafe(32)   # e.g. "sk_abc123..."

# 2. Hash it before storing
key_hash = hashlib.sha256(raw_key.encode()).hexdigest()

# 3. Store only the hash (in uploads/.keys/{file_id}.key)
# 4. Return the raw key to the user ONCE — never stored in plain text

# On each API request:
incoming_hash = hashlib.sha256(x_api_key.encode()).hexdigest()
if incoming_hash != stored_hash:
    raise HTTPException(401, "Invalid API key")
🔐
Why SHA-256 hashing?
Even if someone gains access to the server filesystem, they only see hashes — they cannot recover the original API keys. This follows the same pattern used by GitHub and npm for their tokens.

CORS Configuration

Cross-Origin Resource Sharing is configured in main.py using FastAPI's CORSMiddleware. Origins are read from ALLOWED_ORIGINS in .env — so in production you add only your actual frontend domain, not *.

Input Validation

  • All request bodies are validated with Pydantic models — invalid data returns 422 Unprocessable Entity automatically
  • File extension is checked before processing — only known formats accepted
  • File size is checked against MAX_UPLOAD_SIZE_MB before saving
  • Cloud URIs are parsed and validated before any SDK call is made
  • UUID file IDs prevent path traversal attacks — files are always accessed as uploads/{uuid}.ext

Interview Questions & Answers

30+ likely follow-up questions with honest, easy-to-understand answers.

About the Project

Q1 Why did you build this project?
I wanted to build something end-to-end that combines data engineering with web development. Every data scientist I know wastes hours writing the same "first look at data" code — nulls, dtypes, distributions. I wanted to automate that completely, and also learn FastAPI, React, and Docker in a real project rather than a tutorial.
Q2 Walk me through what happens when a user uploads a file.
  1. User drags a file onto the React dropzone component
  2. Frontend sends a POST /api/upload request with the file as multipart form data
  3. FastAPI saves the file to uploads/ with a UUID as filename to avoid conflicts
  4. The upload route returns a file_id and some metadata
  5. React immediately navigates to /dashboard/{file_id}
  6. The dashboard makes a GET /api/analysis/{file_id} call to get stats
  7. The backend loads the file with the appropriate pandas reader and computes all statistics
  8. Results are returned as JSON and rendered in the UI
Q3 What is the difference between the "Separate" and "Combined" folder modes?
Separate mode: Every file is processed independently and gets its own tab in the Multi-Dashboard. Good when the files are completely different datasets.

Combined mode: The backend tries to merge all files into one dataset. First it normalizes column names (lowercase, snake_case), then uses fuzzy string matching with rapidFuzz to find columns that are the same concept but spelled differently (like "customer_name" vs "CustomerName"), then concatenates everything. Good when you have monthly files of the same data structure.
Q4 How does the selective cleaning work?
There are two API calls involved. First, GET /api/clean/{file_id}/options scans the dataset and returns a list of detected issues — each issue has an ID, a label, and a severity level (error/warning/info). The frontend shows these as a checklist. The user checks only what they want to fix, then clicks Apply. The second call POST /api/clean/{file_id} receives the selected operation IDs in the request body and applies only those operations. So if you only want to remove duplicates and fill missing values in one column, you can do exactly that.

Interview Questions & Answers

Technical deep-dive questions.

Technical Questions

Q5 Why FastAPI instead of Flask or Django?
Three main reasons: (1) Speed — FastAPI is one of the fastest Python frameworks, comparable to Node.js, because it's built on Starlette which uses async I/O. (2) Automatic docs — it generates a Swagger UI at /docs automatically from my code, which is great for development and sharing. (3) Pydantic — all request/response bodies are validated automatically with type hints, so I get input validation for free without writing extra code.
Q6 Why do you use PySpark for large files? Couldn't Pandas handle it?
Pandas loads the entire file into RAM as a DataFrame. A 500 MB CSV might expand to 2–3 GB in memory because of Python's object overhead. On a machine with 8 GB RAM, that can cause an OOM (out of memory) crash. PySpark processes data in chunks (partitions) and can spill to disk when needed, so it can handle files that are much larger than available RAM. I auto-switch at 100 MB — below that Pandas is faster because there's no JVM startup overhead.
Q7 How do you handle file storage? Did you consider a database for files?
Files are stored on the local filesystem in uploads/, cleaned/, and reports/ directories. I intentionally avoided storing binary data in a database because it's much slower and makes the DB grow huge. The UUID filename acts as the primary key. For production at scale, the right upgrade would be to store files in object storage like AWS S3 or Azure Blob and just store the URL in the database — that's actually what Docker volumes enable even now, by mounting those folders as volumes outside the container.
Q8 How does the API key authentication work?
When a user generates an API key, I use Python's secrets.token_urlsafe(32) to generate a cryptographically random key. I then compute its SHA-256 hash and store only the hash to disk. The raw key is shown to the user once and never stored. When an API request comes in with the key in the X-API-Key header, I hash the incoming key and compare it to the stored hash. This means even if an attacker reads the server's file system, they can't recover any API keys.
Q9 Why does the Plotly import use plotly.js/dist/plotly instead of just plotly.js?
This was an actual bug I hit during development. import Plotly from 'plotly.js' imports the raw source, which has a dependency on Node.js's buffer module that doesn't exist in the browser. Vite's bundler throws a "Cannot resolve 'buffer/'" error. The fix is to import from plotly.js/dist/plotly — the pre-bundled browser build that has no Node.js dependencies.
Q10 How does cloud import work under the hood?
The user pastes a URI (like s3://my-bucket/data/sales.csv) and selects the provider. The React component sends a POST to /api/cloud/import with the provider name, URI, and import type (file or folder). The backend parses the URI to extract bucket and key/prefix, then calls the appropriate SDK — boto3 for AWS, azure-storage-blob for Azure, google-cloud-storage for GCP, databricks-sdk for Databricks. The file is downloaded to the local uploads/ folder with a new UUID name and then processed exactly like a local upload. Credentials are read from .env and never exposed to the frontend.
Q11 Why Docker? What does the docker-compose.yml set up?
Docker solves the "works on my machine" problem. The docker-compose.yml defines two services: the backend (Python 3.11 slim + Java for PySpark, runs uvicorn on port 8000) and the frontend (a multi-stage build: Node builds the React app, then nginx serves the static files on port 80 and proxies /api/* requests to the backend). Volumes are mounted for uploads/, cleaned/, and reports/ so data persists even if the containers restart.
Q12 What is CORS and why is it needed here?
CORS (Cross-Origin Resource Sharing) is a browser security feature. When the React app at localhost:5173 tries to call the FastAPI backend at localhost:8000, the browser blocks it because they're on different ports (different "origins"). CORS middleware on the backend tells the browser "yes, requests from localhost:5173 are allowed." In production I would restrict ALLOWED_ORIGINS to only the actual frontend domain — never use * (allow all) in production.
Q13 How does the multi-stage Docker build for the frontend work?
Stage 1 (build): Uses a Node.js image, copies the source, runs npm ci && npm run build. This produces a dist/ folder with just HTML, CSS, and JS — no Node.js runtime needed. Stage 2 (serve): Uses a lightweight nginx image, copies only the dist/ folder from Stage 1. The final image is tiny (≈25 MB) because it doesn't include Node.js or node_modules. nginx also has a config that proxies /api/* to the backend container.

Data, design, and behavioral questions.

Data & Design Questions

Q14 How do you detect outliers?
I use the IQR (Interquartile Range) method. For each numeric column: calculate Q1 (25th percentile) and Q3 (75th percentile), then IQR = Q3 - Q1. Any value below Q1 - 1.5 × IQR or above Q3 + 1.5 × IQR is flagged as an outlier. This method is robust because it's based on percentiles and not affected by the outliers themselves. I chose it over Z-score because Z-score assumes a normal distribution, while IQR works for any distribution.
Q15 How do you fill missing values?
The strategy depends on the column type. For numeric columns, I fill with the column median (more robust than mean because it's not skewed by outliers). For categorical/text columns, I fill with the string "Unknown". This is exposed as a cleaning option per column — the user can choose to apply it or skip it for any specific column.
Q16 What would you do differently if you had to scale this to 100,000 users?
Several things: (1) File storage — move to S3/Azure Blob instead of local disk. (2) Processing — use a task queue like Celery + Redis so large file processing happens in the background and doesn't block HTTP requests. (3) Database — move from optional PostgreSQL to a required one for all metadata. (4) Caching — cache analysis results in Redis since the same file's stats don't change. (5) Horizontal scaling — the backend would need to be stateless (no local files) to run multiple instances behind a load balancer.
Q17 How does fuzzy deduplication work in combined mode?
When merging multiple files, column names might be slightly different — "CustomerName", "customer_name", "cust_name" all mean the same thing. I use rapidFuzz (a fast implementation of fuzzy string matching) to compute similarity ratios between column names across files. If two column names have a similarity above a threshold (e.g., 85%), they're treated as the same column. This handles real-world messy data where different people named columns slightly differently.
Q18 What is the Database used for? The app seems to work without it.
Exactly — the database is optional and stores only metadata (not the files themselves): file ID, original filename, upload source, file format, file size, and upload timestamp. This lets you build features like an upload history page or search past uploads. Without it, the app is fully functional but stateless — if you restart the server, you lose track of which file IDs exist (though the files themselves are still on disk).

Behavioral Questions

Q19 What was the hardest bug you fixed?
The Plotly build error was tricky. The frontend built fine in development but failed with "Cannot resolve 'buffer/'" when I ran npm run build. After debugging I traced it to the Plotly import — import Plotly from 'plotly.js' imports the source code which has a Node.js dependency. The fix was switching to plotly.js/dist/plotly (the pre-built browser bundle). I learned that for browser-targeted libraries you always want the dist build, not the source.
Q20 What would you add next to improve this project?
A few things I'd prioritize: (1) Async processing — use Celery so large files don't timeout the HTTP request. (2) User accounts — OAuth login so users can access their upload history. (3) AI suggestions — use an LLM to describe what patterns it sees in the data in plain English. (4) Data versioning — track cleaning history so you can undo/redo. (5) Export to more formats — not just cleaned CSV, but also Parquet or directly push to a database table.
Q21 How did you make the UI responsive?
I used Tailwind CSS's responsive prefixes. The home page is a two-column layout on desktop (lg:grid-cols-2) and single-column on mobile. The multi-file dashboard has a sidebar on desktop and a horizontal scroll file picker on mobile (hidden with hidden lg:block). All dashboards use max-w-screen-2xl to fill wide monitors. The tab bars use overflow-x-auto so they scroll horizontally on small screens instead of wrapping badly.
Q22 How would you add user authentication to this project?
I'd add a /auth route with POST /auth/register and POST /auth/login. Login would return a JWT (JSON Web Token) signed with a secret key. The frontend stores the JWT in memory (or localStorage) and sends it as an Authorization: Bearer {token} header on every request. FastAPI's Depends system would extract and verify the JWT on each protected route. Each uploaded file would be linked to a user ID so users only see their own data.
Q23 Why Kafka instead of a simple database queue for the streaming pipeline?
Kafka is a distributed log, not just a queue. It has three key advantages here: (1) Durability — events are persisted on disk and replayed if the Spark consumer crashes. A DB queue would need manual dead-letter handling. (2) Decoupling — the ingest API just appends to Kafka; it doesn't need to know anything about the Spark consumer. (3) Scalability — Kafka handles millions of messages per second. A Python DB queue would become a bottleneck under high ingest load. For this project, Kafka is admittedly over-engineered — but it demonstrates production patterns.
Q24 Explain the 1-minute tumbling window aggregation in PySpark.
Each event has a timestamp ts. PySpark's window(col("ts"), "1 minute") groups events into non-overlapping 1-minute buckets (e.g. 10:00–10:01, 10:01–10:02). For each bucket we compute: total event count, sum of is_error (1 if level=ERROR else 0), and average response time. The trigger(processingTime="30 seconds") means Spark re-evaluates windows every 30 seconds — so a window appears in the dashboard within 30 s of its first event, and gets updated as more events arrive within that minute. outputMode("complete") rewrites all window rows on each trigger.
Q25 How does the REST ingest API authenticate callers?
Callers send their API key in the X-API-Key header. The backend computes SHA-256(key) and looks up the hash in the stream_api_keys table. If a matching, active row exists, the request proceeds; otherwise it returns 401 Unauthorized. The plain key is never stored anywhere — only the hash. This means even a database breach doesn't expose valid keys. The design mirrors how Stripe and GitHub store personal access tokens.
Q26 How did you handle the "Kafka not available on localhost" problem?
Kafka inside Docker advertises itself using the Docker service hostname kafka:9092. That hostname is only resolvable inside the Docker network — local Python scripts running on the host can't find it. The fix was to configure dual listeners in docker-compose.yml: PLAINTEXT://localhost:9092 (for host-side scripts) and PLAINTEXT_INTERNAL://kafka:29092 (for Docker-internal services). KAFKA_ADVERTISED_LISTENERS is the critical setting — Kafka tells clients which address to use after the initial bootstrap, and it must be an address the client can actually reach.
Q27 How does the dashboard filter events by service?
The frontend sends GET /api/stream/metrics?service=payment. In the backend, the service query param is optional. Without it, the endpoint reads from stream_metrics (pre-aggregated by the Spark job). With it, the endpoint reads raw events from stream_events and computes the aggregation in SQL on the fly — this is more accurate for the current minute because the Spark window hasn't closed yet. The trade-off is slightly higher DB load, but for small services tables it's negligible.
Q28 Why did you use foreachBatch in the Spark consumer instead of a JDBC sink?
PySpark's built-in JDBC sink uses outputMode("append") which appends a new row on every trigger, creating duplicates for the same window on each batch. foreachBatch gives me full control: I run an INSERT … ON CONFLICT (window_start) DO UPDATE statement (PostgreSQL upsert), so each window row is created once and updated in place as more events arrive within that minute. This is idempotent and exactly-once from the database perspective.
